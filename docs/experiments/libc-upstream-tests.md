# Design: libc upstream tests on OpenHarmony

Status: the unmodified upstream target remains build-blocked. A bounded ARM64 /
API 26 ABI profile has one successful guest run; see [findings](libc-upstream-findings.md).
Date: 2026-10-16.

The first Rust adapter and manual workflow are implemented for review. See
[experiment usage](libc-upstream-usage.md) for commands and evidence semantics.
Full-target build/runtime and bounded-profile repeatability remain unverified.

## 1. Objective

Determine whether a pinned upstream libc test target can be cross-compiled with
our verified OHOS SDK and executed in the existing Oniro guest, producing useful
ABI evidence or a reproducible blocker. Reuse upstream assertions rather than
reimplementing libc's test suite.

The existing file-round-trip fixture remains a fast behavioral smoke test. Its
success proves the deployment recipe works; it does not establish ABI coverage
or upstream test-suite compatibility. The first Rust runtime success is
[38699405669](https://github.com/rust-on-ohos/ohos-rs-pulse/actions/runs/38699405669).
Remaining repeatability checks can proceed independently of this design.

This experiment supplements ecosystem testing. It neither executes the Rust
compiler/standard-library test suite nor changes OHOS's official Rust target tier.
Tier 1 promotion and integration into Rust's own CI are separate projects.

## 2. Scope and pinned inputs

| Input | Initial selection |
|---|---|
| Upstream | rust-lang/libc, release tag 0.2.190 resolved to a reviewed commit |
| Test package | libc-test from the same source tree |
| First test target | ctest only, with its upstream custom harness |
| Rust / cargo-ohos | 1.99.0 / 0.3.4 |
| SDK | 6.1.0.31 / API 23; download release selector 6.1 |
| Target | x86_64-unknown-linux-ohos |
| Guest | Existing Oniro v6.1 image and digest from config/runtime.json |
| Execution context | Existing hdc root-shell context; not an application sandbox |

Resolve and record the tag's commit before implementing the recipe. Fetch by
commit after that review; do not follow a moving branch or latest release.
Record upstream tree identity, lockfile digest, test generator version, resolved
features and any local patches. The Git checkout supplies libc through the test
package's path dependency; this is a source-tree test, not a dependency on the
published crate archive alone.

Pinning is per invocation, not a permanent restriction to 0.2.190. The long-term
flow is scheduled upstream release discovery, immutable commit/lockfile selection,
execution and version-indexed evidence. A future scheduler must preserve previous
attempts and surface unsupported harness changes. First validate this recipe;
automatic release discovery is a subsequent deliverable.

Use the upstream lockfile with --locked initially. If it is absent or unsuitable,
stop and establish a reviewed experiment lockfile as an explicit input change;
do not silently regenerate dependencies. Retain license notices for redistributed
source and generated diagnostics as applicable.

Excluded from the first attempt: cargo test --workspace, feature matrices, other
architectures, other crates, all libc runtime behavior tests, Rust std/rustc
suites, ArkTS, database work and an automatic target-tier promotion proposal.

## 3. What upstream already provides

At tag 0.2.190, libc-test defines ctest with harness = false. Its test source
includes Rust output generated by build/main.rs. The target helper treats the
ohos environment as musl for test configuration. This is a selection rule, not
proof that all ordinary musl assumptions are valid for OpenHarmony.

ctest generates comparisons between Rust FFI definitions and C headers, including
sizes, alignments, struct fields, constants and function signatures. Some checks
happen during compilation/linking; generated comparisons may also require target
execution. Findings must identify which check failed and at which stage.

The first attempt must inspect the pinned generator and generated output to
establish exactly how completion and nonempty coverage can be verified. Do not
assume this executable implements Rust libtest's --list or summary format.

## 4. Build experiment

1. Provision the same pinned SDK/tools as the working smoke test. Preserve setup
   logs and verify actual installed versions before target compilation.
2. Obtain the reviewed upstream checkout in an isolated work directory. Record
   clean/dirty state; retain exact patches when modified.
3. Resolve the libc-test package and its ctest target using Cargo metadata.
   Capture dependency versions/features and host-side build dependencies.
4. Configure Rust linking and the C compiler using cargo-ohos's target environment.
   Verify SDK sysroot, target C flags, include paths and compiler target. C probes
   must use OHOS headers, not Ubuntu headers or a host compiler accidentally.
5. Compile only libc-test's ctest target into a fresh target directory. Capture
   Cargo machine-readable artifact records and separate stderr diagnostics.
6. Select exactly one executable belonging to that package/test/target. Reject
   absent, ambiguous, host-architecture or stale artifacts. Inspect ELF machine,
   interpreter, dependencies and digest before deployment.

Candidate recipe, to be verified rather than copied into production unchanged:

```sh
# From the pinned upstream source tree, with the verified target environment.
cargo ohos test -t x86_64-unknown-linux-ohos \
  --locked -p libc-test --test ctest --no-run \
  --message-format=json --target-dir <fresh-target-directory>
```

Confirm cargo-ohos 0.3.4 supports this forwarding path and that the selected
release's workspace/package configuration matches it. If it does not, evaluate
standard cargo test --target under the verified exported environment. Record the
exact successful argument vectors and environment allowlist. Build dependencies
execute on the host; generated C/Rust test objects must target OHOS.

A separate cargo check is not automatically meaningful for a generated ABI test.
Do not label the existing smoke fixture's check/link statuses as upstream-suite
results. The experiment initially records preparation, test-build, artifact
inspection, execution and cleanup under its own evidence format.

## 5. Runtime experiment

Reuse the proven Rust subprocess and hdc transport implementation. Provisioning
remains in the manual Actions workflow; no new Python orchestration is introduced.

- Allocate a new invocation ID and private guest directory for every attempt.
- Verify guest identity and required interpreter; deploy the selected executable.
- Verify deployed bytes through a guest digest tool when available. If unavailable,
  retain that limitation explicitly; a successful transfer is not a digest check.
- Resolve actual dynamic dependencies with the guest loader and preserve output.
- Execute the reviewed target with a fresh working directory and explicit arguments.
  Capture stdout/stderr separately and the real guest exit code independently of
  hdc's host exit status. Retain the exit-channel probe and fresh shell markers.
- Preserve test evidence before cleanup. Remove only this invocation's files;
  retain unexpected leftovers as diagnostics and report cleanup failure.
- Bound every subprocess. On timeout, terminate host process groups and attempt
  tracked guest-process cleanup; workflow teardown stops the disposable guest.

Initial budgets: test-build 15 minutes, target execution 120 seconds, transport
30 seconds per operation, workflow 45 minutes. These are experimental bounds,
not reliability claims. Guest discovery can approach the current transport budget;
review it separately using measured results. No automatic retries erase failures.

## 6. Completion and coverage acceptance

The file-round-trip JSON completion record does not apply to upstream tests.
Do not modify upstream assertions solely to emit our fixture's record.

Before enabling a passing result, establish a version-specific adapter for the
pinned ctest generator/harness that proves:

1. The executable is the selected upstream test artifact from this attempt.
2. The generated checks are nonempty and their coverage inventory is retained.
3. The execution reached the harness's normal completion path, with the expected
   reviewed summary/completion semantics and zero guest exit status.
4. Reported failures are zero, and any available counts agree with the expected
   inventory. Do not fabricate individual pass counts from the process exit code.
5. Required cleanup succeeded.

Retain generated Rust/C sources and generator configuration for coverage review.
Identify upstream skip rules and applicable cfg exclusions separately from executed
checks. Some conditions may require manual review; do not invent an exact skipped
count where the generator cannot provide one. Ignored or compiled-out checks do
not become passed checks.

If the pinned harness lacks a dependable completion/count interface, document the
blocker and decide whether a minimal generator instrumentation patch is necessary.
Preserve that patch, its rationale and an instrumentation label in evidence. An
external wrapper printing success after exit zero does not prove that assertions
executed. Do not declare passed while this acceptance question is unresolved.

## 7. Outcome and attribution

| Observation | Outcome |
|---|---|
| Tool, fetch, SDK, guest or transport setup fails | infra_error at that phase |
| Target test code fails to compile or link | failed at test-build; cause remains open |
| Failed preparation/build prevents requested execution | blocked execution with predecessor reference |
| Phase exceeds its budget | timed_out; attribution remains open |
| Executed upstream assertion or completion criterion fails | failed execution |
| Build/execute/coverage/cleanup criteria all satisfied | passed for the selected ctest target only |
| Runtime intentionally omitted | not_run |

A test-build failure may reveal absent OH test configuration, unsupported headers,
a Rust binding mismatch, a generator issue or environmental configuration. Preserve
the raw diagnostic; do not infer crate incompatibility from an error keyword.

Start with unmodified upstream sources. Any new skip requires a precise reason,
its affected checks, a source/issue reference and explicit reporting. Never silently
extend ordinary musl skip lists to make OH green. Keep original failure evidence
and patched reruns distinct. Confirmed binding/test fixes should be prepared for
manual upstream review; sending issues or PRs is not part of this design task.

If assertions fail and cleanup also fails, retain the assertion failure and attach
cleanup diagnostics. If assertions pass but required cleanup fails, the overall
execution is infra_error with successful assertion evidence retained.

## 8. Evidence and CLI boundary

Keep the existing file-round-trip run.json version 1 unchanged. Its validator
assumes one reviewed executable, a matching JSON record and fixed stage semantics;
it must not be bypassed or populated with invented upstream results.

The first upstream experiment uses a separately named, versioned experimental
JSON result, generated in Rust, with a summary derived from it. Its exact schema
and CLI invocation are implementation decisions to review before the first run.
Required groups are:

- Invocation/CI identity and source/pin/configuration snapshots.
- Upstream commit, package/target, features, lockfile and patch digests.
- Build environment, SDK/C compiler/sysroot and generator identity.
- Phase outcomes, commands, bounded durations, exit codes and separate logs.
- Generated-check inventory, skips/exclusions and completion interpretation.
- Selected executable identity and inspection evidence.
- Actual guest identity, expected image profile, image verification evidence,
  exit/assertion output and cleanup diagnostics.

Retain artifact discovery JSON, generated sources and relevant diagnostics without
uploading all intermediate target objects. Upload evidence even on failure; setup
failure must not invent an assertion result. GitHub retention is initially 14 days.
SDK archive provenance verification remains unresolved and disclosed independently
of the emulator archive digest check.

Extract reusable Rust execution/transport code only as this adapter requires.
Do not first build a generic crate scheduler, arbitrary command runner or matrix
framework. Fixture configuration and upstream source/test-target selection should
be explicit typed inputs; neither is an executable shell string from configuration.

## 9. Delivery and acceptance

| Step | Deliverable | Exit evidence |
|---|---|---|
| A. Recipe review | Reviewed commit, lockfile/features, generator/completion review | Inputs pinned; acceptance interface known or documented blocker |
| B. Build attempt | Rust orchestration for exactly one target | Real hosted build result and artifact discovery/diagnostics |
| C. Runtime attempt | Manual workflow using existing guest provisioning | Actual guest outcome or explicit execution blocker; complete evidence |
| D. Coverage review | Explain generated, executed and excluded checks | No empty-suite pass or hidden skips; limitations visible |
| E. Repeatability | At least three independent attempts of the final recipe | Distinct evidence and duration/failure review |

The first experiment is complete when one real hosted attempt produces inspectable
build/runtime evidence or a reproducible blocker. Positive compatibility is not
required. Expanding beyond ctest requires reviewing that result and the maintenance
cost. Acceptance for dependable recurring validation additionally requires the
repeatability review.

## 10. Open decisions before implementation

- The exact resolved upstream commit and lockfile/tool compatibility.
- cargo-ohos test forwarding, generated artifact paths and OHOS C configuration.
- The pinned harness's completion and coverage-inventory interface.
- Required source/runtime files and dependency deployment beyond the executable.
- Whether OH-specific test configuration changes are necessary; each needs evidence.
- The experimental JSON contract and minimal Rust CLI adapter entry point.

These are experiment questions, not claims that upstream tests currently run on OH.
